# MoLumen Master Operating Manual

## Mission
Build and maintain Mo Lumen Astrology as a premium, warm, authoritative astrology platform.

Immediate goal: increase qualified paid reading bookings.

Secondary goals:
- grow the Kit newsletter list
- strengthen trust and third-party corroboration
- build search authority
- improve AEO/GEO readiness
- maintain a durable educational knowledge base
- support YouTube/video publishing
- prepare for future reports, memberships, courses and products

## Brand
The site should feel intelligent, warm, personal, sophisticated, grounded, contemporary, slightly mysterious without cliché, and premium without being corporate.

Avoid generic astrology tropes, purple-gradient overload, mystical stock imagery, fake urgency, fear-based astrology, guarantees, and deterministic claims.

## Product philosophy
Astrology is presented as interpretation and perspective, not deterministic certainty. Preserve agency-first language and distinguish:
1. astronomical fact
2. astrological tradition/doctrine
3. modern practice
4. Mo's interpretation/synthesis

## Autonomous authority
Claude may decide routine matters involving code structure, components, CSS, responsive behavior, accessibility, SEO implementation, metadata, schema structure, internal linking, performance, tests, publishing workflows, Kit integration mechanics, YouTube facade architecture, analytics events, and safe copy cleanup.

Do not stop for technically equivalent implementation choices.

## Never invent
Do not fabricate services, prices, durations, testimonials, reviews, credentials, client outcomes, policies, legal facts, products, courses, event dates, astronomical facts, third-party verification, analytics results or source citations.

## Evidence
Use:
- Measured — tests/runtime/source
- Observed — visible/code-derived
- Advisory — UX/CRO/editorial judgment

Never present advisory judgment as measured evidence.

## Repository principles
- Fix shared root causes first.
- Preserve working analytics, booking, forms and schema.
- Prefer reusable content collections/templates.
- Keep static-first architecture unless server logic is genuinely required.
- No production deploy or DNS cutover without explicit instruction.

## Quality gates
Before finishing material work:
- build succeeds
- framework/type checks succeed
- links succeed
- relevant booking tests succeed
- relevant accessibility tests succeed
- console errors reviewed
- responsive layouts reviewed
- metadata/schema validated
- regressions corrected

## Content ownership
Mo should be able to maintain ordinary content without editing layout code.
